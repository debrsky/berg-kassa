# Инструкции для агентов — Berg Kassa

## Контекст

Это WebUI для кассовых операций в PostgreSQL с выбором рабочей схемы. Основной стек: PHP (PDO/PostgreSQL), JavaScript и CSS без фронтенд-сборки; миграция из MSSQL написана на Python. Интерфейс и документация — на русском. Перед изменением поведения сверяйтесь с `README.md` и `docs/webui-spec.md`; сценарии ручной приёмки — в `docs/Чек-лист приемки Кассы обычным пользователем.md` и `docs/Чек-лист приемки Кассы суперпользователем.md`.

## Карта проекта

- `public/index.php` — HTTP-маршруты и HTML-страницы; `public/router.php` — маршрутизатор встроенного PHP-сервера; `public/css/`, `public/js/` — стили и клиентская логика.
- `src/bootstrap.php` — загрузка окружения и сессии; `src/app.php` — БД, ответы и фильтры; `src/auth.php` — пользователи, авторизация, выбор схемы и аудит; `src/operations.php` — операции и итоги; `src/references.php` — справочники; `src/navigation.php` — навигация.
- `migrate_trading.py` — перенос данных из MSSQL; `bin/` — административные, резервные и деплой-скрипты.
- `tests/unit/`, `tests/integration/`, `tests/e2e/`, `tests/test_migrate_trading.py` — тесты PHP, БД, Playwright и мигратора.

## Правила изменений

- Сохраняйте разделение схем: `auth` содержит пользователей и аудит; операции и справочники живут в выбранной схеме данных. Проверяйте разрешённые пользователю схемы и используйте существующий `useDataSchema()` до запросов к таблицам данных. Не подставляйте пользовательский ввод в SQL; применяйте параметризованные запросы и проверку идентификаторов схем.
- Не ослабляйте проверки сессии, `X-CSRF-Token`, `can_view_protected`, скрытие защищённых операций и запись событий в `auth.audit_log`. Для новых изменяющих API следуйте существующим обработчикам в `src/auth.php`, `src/operations.php`, `src/references.php`.
- Учитывайте точность денежных сумм и ставок, правила фильтрации и итоги; не заменяйте серверные вычисления арифметикой с плавающей точкой в браузере.
- При изменении API обновляйте соответствующий JS и тесты; при изменении интерфейса проверяйте desktop и mobile. Не добавляйте сборку фронтенда без необходимости.
- `.env` содержит секреты и игнорируется Git: не печатайте его значения в логах/ответах и не коммитьте. Используйте `.env.example` только как шаблон. Не запускайте миграцию с `--apply`, восстановление с `-Replace`, деплой или другие потенциально разрушающие действия без явного запроса; по умолчанию мигратор работает без записи (`python migrate_trading.py`).

## Запуск и проверки

Проект ориентирован на Windows/PowerShell. Локальный PHP: `.tools/php/php.exe`; запуск: `./start-local.cmd` (порт 8080). Требуются настроенный `.env` и PostgreSQL; E2E используют учётные записи `E2E_*` из окружения. Playwright по умолчанию сам поднимает PHP-сервер на порту 18090 (`playwright.config.js`).

- Все проверки: `npm test` (статика, PHP unit, интеграция с БД, Playwright). Предварительно: `npm install` и `npx playwright install chromium`.
- Выборочно: `npm run test:static`, `npm run test:unit`, `npm run test:integration`, `npm run test:e2e`; Python-тесты: `python -m unittest discover -s tests -p 'test_*.py'`.
- Интеграционные и E2E-тесты требуют доступной БД и настроенных пользователей; если окружение не готово, сообщите, какие проверки не удалось выполнить. Не используйте реальные данные для тестовых записей.
