# Проверка HTML и качества интерфейса

Проверена рабочая версия на основе коммита `d6f3f30`, 4 сентября 2026 года.
Требования: раздел 8.2 [ТЗ](webui-spec.md). После аудита объём приёмки сокращён
по решению пользователя: отдельные валидаторы, скринридеры и дополнительные
браузеры не требуются. Ниже сохранены фактические границы проведённой проверки. Итог: **частичное соответствие**.
Прохождение функциональных тестов не означает соответствие всем требованиям
HTML или WCAG. Первоначальный аудит не изменял код. После него по запросу пользователя
выполнены исправления; актуальный статус см. ниже.

## Объём и метод

- Просмотрены PHP-разметка, JS всех пяти страниц, CSS и серверные проверки.
- `npm test`: статическая проверка успешна, **14 unit, 18 schema/integration,
  48 API/UI** проверок прошли, пропусков нет.
- Локально выполнен axe-core **4.13.0**, наборы WCAG 2 A/AA, 2.1 AA, 2.2 AA;
  Chromium **151.0.7922.34**. Инструмент использован временно через `npm pack`,
  зависимости и lock-файл приложения не изменены.
- Проверены `/login`, `/`, `/references`, `/audit`, `/users` с тестовым
  пользователем с защищённым доступом; дополнительно главная страница в тёмной
  теме и открытая форма новой операции. Тесты проекта отдельно проверяют
  ограниченного пользователя, меню, клавиатурный Escape и поля дат.
- На этих состояниях измерена ширина документа при viewport 1280, 640, 390,
  320 CSS px. Это проверка переполнения, не полная визуальная приёмка.
- Ошибка выхода воспроизведена перехватом `/api/logout` с сетевым отказом.
- При отключённом JS отправка формы входа проверена вымышленными данными:
  запрос перехвачен и отменён до отправки на сервер.
- На `https://kassa.bergvl.ru/login` проверены публичные HTTP-заголовки и
  перенаправление с HTTP. Закрытые страницы хостинга отдельно не аудировались.

## Подтверждённые нарушения

| Приоритет | Требование | Наблюдение и воспроизведение | Где исправлять |
|---|---|---|---|
| Высокий | FORM-01, SEC-01 | При отключённом JS форма входа отправляет GET с полями `login` и `password` в URL. У формы отсутствуют `method` и `action`; `noscript` отсутствует. В обычном режиме JS перехватывает отправку, но при его отказе пароль может попасть в историю и журналы запросов. ## Результаты axe-core и ограничения

- `/login`, тёмная главная страница, открытая форма операции, `/references`,
  `/audit`, `/users`: в выбранных наборах правил автоматических нарушений не
  обнаружено. Это не означает полного соответствия WCAG.
- Светлая главная страница: нарушение `color-contrast` в заголовках колонок.
- `incomplete`: `aria-prohibited-attr` на главной странице и `color-contrast`
  на странице справочников требуют дополнительной ручной оценки. Они не
  засчитаны ни как успешные проверки, ни как доказанные нарушения.
- Системная тема отдельно не сканировалась; axe не запускался для каждого
  состояния меню, всех форм справочников и всех размеров viewport.
- Проверка отсутствия переполнения не доказывает отсутствие перекрытий и
  доступность каждого элемента. Скринридер, touch-устройства и browser zoom
  остаются отдельной работой.

## Хостинг

HTTP `/login` возвращает 301 на HTTPS; HTTPS возвращает 200. В ответе есть
`Content-Security-Policy`, HSTS, `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY`, `Cache-Control: no-store…` и `X-Robots-Tag: noindex…`.
Это подтверждает настройку заголовков публичной страницы, но не заменяет
проверку защищённых сессий и каждого API. Прикладной код и данные на хостинге
в рамках аудита не изменялись.

## Дальнейшая приёмка

Сначала исправить шесть перечисленных нарушений, затем повторить затронутые
сценарии существующими тестами. Отдельный HTML-валидатор, NVDA/VoiceOver и
дополнительные браузеры устанавливать не нужно. Это решение сокращает объём
приёмки, но не отменяет шесть обнаруженных нарушений.
Основания требований: [HTML Living Standard](https://html.spec.whatwg.org/multipage/)
и [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

## Исправления после аудита

Шесть замечаний устранены в коде:

- Формы входа и редактирования явно используют POST; без JS показано сообщение.
  Тест с вымышленными данными перехватывает отправку и проверяет отсутствие
  пароля в URL. Работа приложения без JavaScript не реализуется.
- Ошибка выхода на главной странице, в аудите и пользователях перехватывается,
  выводится в статус и позволяет повторить действие.
- Диалог связан с заголовком через `aria-labelledby`; проверяется доступное имя.
- Заголовки колонок используют основной цвет текста. Тест вычисляет контраст
  из фактических CSS-цветов обеих тем и требует не менее 4,5:1.
- Общие статусы имеют `role=status`. У сообщения формы пользователя эта роль
  уже была; исправлена неточность первоначального отчёта.
- Сохранение пользователя и справочника блокирует кнопку и повторную отправку
  до окончания запроса, включая повторный submit с клавиатуры. После ошибки
  блокировка снимается. Тесты перехватывают запросы, не создавая записи в БД.

Первоначальная матрица выше описывает состояние до исправлений. Проверки
выполняются существующим Playwright без установки новых инструментов.

Повторный полный `npm test` после исправлений: статические проверки успешны,
**14 unit + 18 schema/integration + 56 API/UI = 88 проверок**, без пропусков
и ошибок. Новые браузерные проверки выполнены в настольном и мобильном режимах.

## Рефакторинг и исправления 2026-09-05

Серверные функции разделены на общие функции, авторизацию/аудит, справочники
и операции. Запуск окружения и сессии вынесен в `src/bootstrap.php`;
виртуальный список — в `public/js/virtual-list.js`. Клиентские страницы

снимок записи для аудита, обработка подтверждённого сохранения при последующем
сбое чтения, устаревшая ошибка итогов и разблокировка справочников после
неудачной смены схемы. Десятичные строки округляются без `float`, итоговое
сальдо вычисляется в PostgreSQL через `numeric`.

Проверки включают реальные блокировки двумя соединениями БД для PUT и DELETE,
большие суммы с разницей в одну копейку, повторное сохранение после ошибки
чтения, устаревшую ошибку итогов и блокировку редактора. Полный `npm test`:
**22 unit + 18 schema/integration + 83 API/UI = 123 проверки**, без ошибок
и пропусков; статические проверки успешны. После заключительного упрощения
заполнения формы пользователя повторно прошли обе её браузерные проверки.
