# WebUI «Касса» — техническое задание

## 0. Проверка качества

Проект должен иметь единый запуск `npm test`, включающий статическую проверку
PHP, JavaScript и Python, unit-тесты серверных правил, read-only проверку схемы
и целостности данных, API-тесты и браузерные тесты настольного и мобильного UI.
CRUD-тесты используют временные записи с обязательной очисткой. Нагрузочный
read-only прогон запускается отдельно командой `npm run test:load`.

## 1. Назначение

WebUI предназначен для просмотра, анализа и ведения финансовых операций в PostgreSQL.
Текущая схема выбирается пользователем из доступных ему схем.

Первая версия системы предоставляет одну главную форму с фильтрацией операций,
разделением на приход и расход и расчётом итогов и сальдо.

Интерфейс поддерживает светлую, тёмную и системную цветовую тему. Переключатель
доступен на всех страницах, выбор сохраняется в браузере. Системный режим
следует настройке `prefers-color-scheme` операционной системы. Кнопка имеет
фиксированный размер 36 × 36 px и переключает режимы «Системная → Светлая →
Тёмная». Режим обозначается иконкой монитора, солнца или луны, подсказкой и
доступной подписью для скринридера; размер при переключении не меняется.

## 2. Главная форма

Главная форма состоит из трёх горизонтальных областей:

1. Панель фильтров.
2. Рабочая область из двух расположенных рядом вертикальных панелей:
   «Приход» и «Расход».
3. Панель итогов.

Фильтры и итоговые значения общие для обеих панелей.

На авторизованных страницах навигация собрана в «Меню ▾»: «Справочники»,
«Журнал аудита», «Пользователи» и «Выйти» после разделителя. На внутренних
страницах добавляется ссылка «Операции». Недоступные по правам пункты скрыты.
Меню закрывается после выбора пункта, клика снаружи или Escape; Escape
возвращает фокус на кнопку меню.

## 3. Фильтры

В верхней части формы располагаются:

| Фильтр | Назначение |
|---|---|
| Период | Начальная и конечная дата включительно |
| Счёт | Один счёт из `accounts` выбранной схемы |
| Валюта | Одна валюта из `currencies` выбранной схемы |
| Направление | Элемент из `directions` выбранной схемы |
| Операция | Элемент из `action_types` выбранной схемы |
| Подоперация 1 | Элемент из `suboperations_l1` выбранной схемы |
| Подоперация 2 | Элемент из `suboperations_l2` выбранной схемы |
| Защищённые | Чекбокс, управляющий отображением операций `is_black = true` |

### 3.1. Поведение фильтров

- При первом открытии устанавливается период за последние 30 календарных дней,
  включая текущую дату.
- Пустое значение справочного фильтра означает «Все».
- Поля дат подписаны «С» и «По». Подсказки поясняют включение конечной даты и
  отсутствие ограничения при пустой границе.
- Быстрый выбор «Период» содержит: «Сегодня», «Вчера», «Эта неделя», «Этот
  месяц», «Прошлый месяц», «Последние 30 дней», «За всё время». Выбор сразу
  устанавливает даты и обновляет операции и итоги. Неделя начинается в
  понедельник; текущие неделя и месяц заканчиваются сегодняшней датой.
- Пустое «С» снимает нижнюю границу, пустое «По» — верхнюю; обе пустые даты
  означают «За всё время». Очистка клавиатурой также применяет фильтр, даже
  если браузер первоначально пометил частично удалённую дату некорректной.
- При двух заполненных датах начало не может быть позже конца: интерфейс
  показывает ошибку без применения периода, сервер отклоняет такой запрос.
- Ручная правка сбрасывает выбор готового периода. Пустые границы сохраняются
  в URL и восстанавливаются после перезагрузки; сброс возвращает последние
  30 календарных дней.
- Справочные фильтры реализованы как одиночные списки без текстового поиска.
- Фильтры «Направление → Операция → Подоперация 1 → Подоперация 2» являются
  каскадными.
- Изменение родительского фильтра обновляет доступные дочерние значения и
  сбрасывает несовместимый выбор.
- Если после выбора уровня в следующем фильтре остаётся ровно одна позиция,
  она выбирается автоматически; правило применяется до конца каскада.
- Иерархические фильтры выбираются только последовательно сверху вниз.
- «Операция» недоступна, пока не выбрано направление; «Подоперация 1» — пока не
  выбрана операция; «Подоперация 2» — пока не выбрана подоперация 1.
- Изменение или очистка родительского уровня очищает и блокирует все дочерние
  уровни.
- Выбранные фильтры применяются одновременно к приходу, расходу и итогам.
- Чекбокс «Защищённые» по умолчанию выключен. В этом состоянии отображаются и
  учитываются в итогах только операции с `is_black = false`.
- Если чекбокс «Защищённые» включён, отображаются и учитываются все операции:
  `is_black = false` и `is_black = true`.
- Чекбокс доступен только пользователям с правом `can_view_protected`. Сервер
  проверяет это право независимо от переданных параметров запроса.
- После перезагрузки страницы фильтры восстанавливаются из URL.
- Предусмотрена команда «Сбросить фильтры».

## 3.2. Авторизация

- Пользователь входит по логину и паролю; состояние входа хранится в PHP-сессии.
- Форма входа запрещает браузеру сохранять пароль (`autocomplete="off"`).
- У пользователя заданы доступные схемы данных и право просмотра защищённых
  операций `can_view_protected`.
- Пользователь выбирает текущую схему из массива `auth.users.data_schema`;
  сервер проверяет выбор по этому же массиву.
- Отсутствующая схема помечается в списке как недоступная. API возвращает
  `409 DATA_SCHEMA_NOT_FOUND`, а данные не загружаются до выбора существующей
  схемы.
- Неавторизованный запрос к API возвращает HTTP 401.
- Выход выполняется POST-запросом с CSRF-токеном.

## 3.3. Журнал аудита

- События записываются в append-only таблицу `auth.audit_log` с датой, типом
  события, пользователем, логином, IP-адресом, рабочей схемой и объектом.
- Журналируются успешные и неуспешные входы, блокировка частых попыток, выход,
  выбор схемы, отказы аутентификации/авторизации, а также создание, изменение и
  удаление финансовых операций и справочников.
- Пароли и CSRF-токены в журнал не записываются. Для изменений данных в `details`
  сохраняются прежнее и новое состояния записи.
- Изменение данных и соответствующая запись аудита выполняются в одной
  транзакции PostgreSQL.
- Просмотр журнала не предоставляется через публичный API. Доступ к таблице
  и странице `/audit` разрешён только пользователям с `can_view_protected`;
  сервер проверяет право независимо от видимости ссылки в интерфейсе.
- Страница журнала показывает дату, событие, пользователя, IP, схему, объект и
  JSON-детали. Доступны фильтры по периоду, событию и логину, а также постраничная
  навигация по 50 записей. Изменение и удаление событий через WebUI не допускается.
- Доступ к таблице ограничивается администраторами БД; рабочей роли запрещаются
  `UPDATE` и `DELETE`.
- Срок хранения по умолчанию — 180 дней. Устаревшие события удаляются командой
  `php bin/prune-audit-log.php 180` из доверенного административного окружения.
- `bin/deploy-hosting.ps1` до загрузки новой версии приложения автоматически
  применяет идемпотентную инициализацию схемы `auth` к PostgreSQL хостинга.

## 3.4. Управление пользователями

- Страница `/users` и API `/api/users` доступны только пользователям с
  `can_view_protected`; право проверяется сервером.
- Разрешены просмотр, создание и изменение логина, списка доступных схем,
  активности и права на защищённые операции. Пароль обязателен при создании и
  может быть заменён при редактировании; хеш пароля API не возвращает.
- Пользователь не может отключить собственную учётную запись или отозвать у
  себя право `can_view_protected`. Изменения пользователей записываются в аудит
  без паролей и их хешей.

## 4. Панели операций

Панели «Приход» и «Расход» имеют одинаковую структуру и независимую прокрутку.
При ширине экрана менее 1100 пикселей панели отображаются во вкладках с
сохранением выбранной вкладки в пределах браузерной сессии.

Каждая строка отображает:

| Поле интерфейса | Источник |
|---|---|
| Дата | `actions.action_date` |
| Счёт и валюта | `accounts.name`, `currencies.name` |
| Направление и операция | `directions.name`, `action_types.name` |
| Подоперации 1 и 2 | `suboperations_l1.name`, `suboperations_l2.name` |
| Сумма | `actions.amount` |
| Примечание | `actions.memo` |

Операции сортируются по дате и ID в обратном порядке: сначала новые.

Операции загружаются при прокрутке без видимой постраничной навигации. Каждая
панель имеет независимое положение прокрутки и независимый кэш страниц.

Frontend использует виртуальный список: полоса прокрутки отражает полное число
операций, а в DOM и памяти находятся только видимые строки, небольшой буфер и
не более 20 страниц по 100 операций. Удалённые из LRU-кэша страницы повторно
загружаются при возврате к ним. При перетаскивании ползунка запрос откладывается
на 120 мс, а запросы более неактуальных страниц отменяются.

Backend возвращает операции порциями по 100 строк для позиции, соответствующей
текущему положению полосы прокрутки.

Положение прокрутки преобразуется в `offset`; API возвращает страницу для этого
смещения. SQL сначала выбирает ID нужной страницы по индексу
`(is_debit, action_date DESC, id DESC)`, затем присоединяет справочники.

При изменении любого фильтра обе панели очищаются, запросы устаревших страниц
отменяются, и загрузка начинается с первой страницы. Во время запроса
отображается индикатор загрузки.

### 4.1. Разделение на приход и расход

Разделение выполняется по `actions.is_debit` выбранной схемы:

- `true` — приход;
- `false` — расход.

### 4.2. Отображение значений

- Сумма выводится с двумя знаками после запятой и разделителями тысяч.
- Валюты не смешиваются в одной итоговой сумме без пересчёта.
- Значения `NULL` отображаются знаком `—`.
- Placeholder-элементы справочников отображаются как «Неизвестно (ID: …)».
- Защищённая операция выделяется фоном и цветным акцентом без раскрытия
  дополнительной информации.

## 5. Итоги

В нижней части формы показываются результаты для всей отфильтрованной выборки,
а не только для загруженной страницы. Раздел содержит только таблицу с
заголовками столбцов, без отдельного заголовка, подписи периода и счётчика
операций над ней. Для скринридера сохраняется название «Итоги и сальдо».

### 5.1. Итоги по валютам

Для каждой валюты отображаются:

| Валюта | Начальное сальдо | Приход | Расход | Текущее сальдо | Конечное сальдо |
|---|---:|---:|---:|---:|---:|

### 5.2. Правила расчёта

- Расчёты выполняются в исходной валюте операции.
- `NULL` в сумме не участвует в расчёте.
- Округление выполняется до двух знаков после запятой.
- Начальное сальдо рассчитывается по операциям, дата которых меньше начальной
  даты выбранного периода, с применением остальных активных фильтров.
- Итоговый приход — сумма операций `is_debit = true` внутри выбранного периода.
- Итоговый расход — сумма операций `is_debit = false` внутри выбранного периода.
- Текущее сальдо за период равно `приход − расход`.
- Конечное сальдо равно `начальное сальдо + текущее сальдо`.
- Конечная дата периода включается целиком.
- Использование `exchange_rate` для дополнительного итога в базовой валюте не
  входит в первую версию и требует отдельного правила пересчёта.
- Защищённые операции участвуют в итогах только при включённом чекбоксе
  «Защищённые».

## 6. API первой версии

Backend предоставляет endpoint авторизации и выбора контекста:

```text
POST /api/login
POST /api/logout
GET  /api/me
POST /api/schema
GET  /api/audit-log
```

Данные предоставляются через endpoint:

```text
GET /api/lookups
GET /api/actions
GET /api/action-summary
POST /api/actions
PUT /api/actions/{id}
DELETE /api/actions/{id}
GET /api/references/{type}
POST /api/references/{type}
PUT /api/references/{type}/{id}
DELETE /api/references/{type}/{id}
```

`/api/actions` возвращает одну порцию строк для выбранного типа операции. Тип
передаётся параметром `flow=income|expense`, позиция — параметрами `offset` и
`limit`. При `include_total=1` ответ также содержит полное число строк панели.

`/api/action-summary` возвращает:

- итоги по валютам;
- общее количество найденных операций.

Оба endpoint принимают одинаковые параметры фильтрации. Идентификаторы
справочников передаются как целые числа, даты — в формате `YYYY-MM-DD`.
Явно пустые `from_date=` и `to_date=` снимают соответствующую границу.
Отсутствующий параметр даты использует значение периода по умолчанию;
`all_time=1` снимает обе границы. Без нижней границы начальное сальдо равно
нулю; без верхней границы расчёт включает все операции после начала периода.
Чекбокс «Защищённые» передаётся параметром `include_protected=1`; отсутствие
параметра или значение `0` означает фильтр `is_black = false`.

Справочники для фильтров загружаются через `/api/lookups`.

### 6.1. Добавление, редактирование и удаление

- Компактные кнопки «+ Добавить» находятся рядом с заголовками панелей прихода
  и расхода и открывают модальное окно с уже выбранным типом операции.
- Двойное нажатие на строку открывает ту же форму с данными выбранной операции;
  нажатие на дату открывает её на компьютере и смартфоне.
- Форма содержит тип операции, дату и время, счёт, сгруппированные валюту и курс,
  каскад справочников, сумму, примечание и признак защищённой операции. Для новой
  операции по умолчанию выбирается валюта `р.`.
- При создании операции выбранные справочные фильтры и признак «Защищённые»
  подставляются в одноимённые поля формы; выбранная в фильтре валюта имеет
  приоритет над валютой `р.`.
- Для новой операции раскрываемый раздел «Выполнить проводку» позволяет выбрать счёт и
  подоперацию 2; список подопераций 2 ограничен выбранной в основной части формы
  подоперацией 1. При включении проводки сервер в одной транзакции создаёт вторую
  операцию противоположного типа с теми же датой, суммой, валютой, курсом,
  примечанием и признаком защищённости. После создания операции независимы.
- После выбора каждого уровня каскада следующий уровень выбирается автоматически,
  если в нём доступна ровно одна позиция; правило применяется до конца цепочки.
- При выборе валюты поле курса заполняется последним ненулевым значением из
  `currency_rates` по дате и ID. Для валюты `р.` при отсутствии истории
  используется курс `1`; пользователь может изменить предложенное значение.
- После успешного сохранения или удаления список и итоги обновляются.
- Удаление физически удаляет запись после отдельного подтверждения пользователя.
- Все изменяющие запросы требуют аутентификации и действующий CSRF-токен.
- Авторизованный пользователь может изменять обычные операции в доступной ему
  схеме. Работа с защищёнными операциями доступна только пользователю с правом
  `can_view_protected`.
- Backend проверяет типы и обязательность полей, положительные значения суммы и
  курса, а также существование выбранных записей справочников.

### 6.2. Справочники

Просмотр справочников доступен авторизованным пользователям в разрешённых
схемах. Создание, изменение и удаление доступны только с `can_view_protected`.
Без этого права форма редактирования и кнопки изменения скрыты, а сервер
возвращает HTTP 403 на POST, PUT и DELETE для всех семи справочников независимо
от интерфейса. Просмотр списков, каскада и поиск остаются доступными.

Отдельная страница `/references` позволяет добавлять, редактировать и удалять счета, валюты,
курсы валют, направления, операции и подоперации обоих уровней. Операции и
подоперации отображаются в трёх связанных колонках; направление задаётся над
ними, а каждая колонка имеет поиск и компактную кнопку добавления. Выбор записи
фильтрует следующий уровень, двойное нажатие или кнопка с карандашом открывает
редактирование. На смартфоне уровни перелистываются горизонтально, а форма
редактирования располагается под ними. Для зависимых
справочников форма содержит выбор родительской записи. Ручное изменение
импортированной служебной записи снимает с неё признак `is_placeholder`.

Backend принимает только типы таблиц и поля из жёстко заданного списка. Перед
удалением независимо от ограничений базы проверяются зависимости:

- счёт — операции;
- валюта — операции, счета и курсы;
- направление — операции справочника;
- операция справочника — подоперации 1;
- подоперация 1 — подоперации 2;
- подоперация 2 — финансовые операции.

При наличии хотя бы одной зависимости запись не удаляется, API возвращает
`409 Conflict` с количеством использований. Внешние ключи остаются дополнительной
защитой от конкурентного изменения данных.

## 7. Нефункциональные требования

- Backend: PHP 8.5.
- База данных: PostgreSQL 17; рабочая схема выбирается из профиля пользователя.
- Кодировка ответов: UTF-8.
- Значения фильтров передаются параметрами SQL. Структурные значения SQL
  допускается формировать только после строгой серверной валидации.
- Целевое время ответа для списка и итогов — до одной секунды на текущем объёме
  данных в локальной сети.
- Интерфейс должен корректно работать при ширине от 1280 пикселей.
- При ширине менее 1100 пикселей панели отображаются в отдельных вкладках.
- На смартфонах форма операции открывается на весь экран, её заголовок и кнопки
  действий остаются доступными при прокрутке; интерактивные элементы имеют
  увеличенную область касания.
- Изменение структуры рабочих схем при работе с операциями не требуется.

### 7.1. CSS и дизайн-система

- Имена прикладных CSS-классов строятся по БЭМ:
  `.block__element--modifier`.
- CSS-классы отражают компонент интерфейса, а не его положение или содержимое.
- Токены дизайн-системы, базовая типографика, цвета, отступы, радиусы и состояния
  фокуса находятся в отдельном файле `public/css/design-system.css`.
- Стили компонентов находятся в `public/css/app.css`.
- Компоненты используют переменные дизайн-системы вместо собственных цветов и
  размеров.
- `!important` не используется. Inline-стили допускаются только для вычисляемой
  геометрии виртуального списка и позиционирования popover.

## 8. Критерии приёмки MVP

1. Пользователь задаёт период и любую комбинацию справочных фильтров.
2. Обе панели показывают операции из одной отфильтрованной выборки.
3. Операция отображается только в одной из панелей.
4. Итоги рассчитаны по всей выборке и совпадают с контрольными SQL-запросами.
5. Текущее сальдо по каждой валюте равно приходу минус расходу.
6. Каскадные фильтры не предлагают несовместимые значения.
7. Перезагрузка URL восстанавливает выбранные фильтры.
8. Переход к произвольной позиции загружает соответствующую страницу без
   накопления всей выборки в памяти.
9. При выключенном чекбоксе защищённые операции отсутствуют в панелях и итогах.
10. При включённом чекбоксе панели и итоги включают защищённые и обычные
    операции.
11. Прокрутка остаётся плавной при выборке до 250 000 операций, потому что DOM
    содержит только видимые строки.
12. Полоса прокрутки отражает полный размер выборки, а видимые страницы
    загружаются без кнопок и видимого переключения страниц.
13. Итоги отображаются только по валютам: начальное сальдо, приход,
    расход, текущее и конечное сальдо.
14. Конечное сальдо равно начальному сальдо плюс приход минус расход.
15. Пользователь может добавить и отредактировать операцию через модальное окно.
16. После сохранения операция и пересчитанные итоги отображаются без перезагрузки страницы.
17. Удаление требует подтверждения и удаляет выбранную запись из рабочей схемы.
18. Запрос без корректного CSRF-токена не изменяет данные.
19. Пользователь без `can_view_protected` не может создать, изменить или удалить
    защищённую операцию.
20. Изменение всех семи справочников доступно только с `can_view_protected`;
    без права разрешён просмотр, а изменяющие API-запросы возвращают HTTP 403.
21. Удаление используемой записи справочника блокируется явной серверной
    проверкой даже при отсутствии внешнего ключа.
22. Входы, отказы доступа и CRUD-изменения создают записи `auth.audit_log`, а
    изменение прикладных данных не фиксируется без соответствующего аудита.
23. Страница и API журнала аудита доступны только пользователям с правом
    `can_view_protected`; журнал поддерживает фильтры и постраничный просмотр.
24. Страница и API управления пользователями доступны только пользователям с
    `can_view_protected`; пароли и их хеши не возвращаются клиенту и не попадают
    в журнал аудита.

25. Готовые периоды корректны на границах месяцев и в високосном году;
    очистка любой границы клавиатурой обновляет фильтр и сохраняется в URL.
26. Меню работает на компьютере и смартфоне, закрывается по Escape и клику
    снаружи, сохраняет ограничения прав и позволяет выйти из системы.
27. Кнопка темы сохраняет размер 36 × 36 px во всех трёх режимах.
