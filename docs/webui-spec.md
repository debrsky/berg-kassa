# WebUI «Касса» — техническое задание

## 1. Назначение

WebUI предназначен для просмотра и анализа финансовых операций из PostgreSQL.
Текущая схема выбирается пользователем из доступных ему схем.

Первая версия системы предоставляет одну главную форму с фильтрацией операций,
разделением на приход и расход и расчётом итогов и сальдо.

## 2. Главная форма

Главная форма состоит из трёх горизонтальных областей:

1. Панель фильтров.
2. Рабочая область из двух расположенных рядом вертикальных панелей:
   «Приход» и «Расход».
3. Панель итогов.

Фильтры и итоговые значения общие для обеих панелей.

## 3. Фильтры

В верхней части формы располагаются:

| Фильтр | Назначение |
|---|---|
| Период | Начальная и конечная дата включительно |
| Счёт | Один счёт из `accounts` выбранной схемы |
| Валюта | Одна валюта из `currencies` выбранной схемы |
| Направление | Элемент из `directions` выбранной схемы |
| Операция | Элемент из `action_types` выбранной схемы |
| Подоперация 1 | Элемент из `suboperations_l1` выбранной схемы |
| Подоперация 2 | Элемент из `suboperations_l2` выбранной схемы |
| Защищённые | Чекбокс, управляющий отображением операций `is_black = true` |

### 3.1. Поведение фильтров

- При первом открытии устанавливается период за последние 30 календарных дней,
  включая текущую дату.
- Пустое значение означает «Все».
- Справочные фильтры реализованы как одиночные списки без текстового поиска.
- Фильтры «Направление → Операция → Подоперация 1 → Подоперация 2» являются
  каскадными.
- Изменение родительского фильтра обновляет доступные дочерние значения и
  сбрасывает несовместимый выбор.
- Иерархические фильтры выбираются только последовательно сверху вниз.
- «Операция» недоступна, пока не выбрано направление; «Подоперация 1» — пока не
  выбрана операция; «Подоперация 2» — пока не выбрана подоперация 1.
- Изменение или очистка родительского уровня очищает и блокирует все дочерние
  уровни.
- Выбранные фильтры применяются одновременно к приходу, расходу и итогам.
- Чекбокс «Защищённые» по умолчанию выключен. В этом состоянии отображаются и
  учитываются в итогах только операции с `is_black = false`.
- Если чекбокс «Защищённые» включён, отображаются и учитываются все операции:
  `is_black = false` и `is_black = true`.
- Чекбокс доступен только пользователям с правом `can_view_protected`. Сервер
  проверяет это право независимо от переданных параметров запроса.
- После перезагрузки страницы фильтры восстанавливаются из URL.
- Предусмотрена команда «Сбросить фильтры».

## 3.2. Авторизация

- Пользователь входит по логину и паролю; состояние входа хранится в PHP-сессии.
- У пользователя заданы доступные схемы данных и право просмотра защищённых
  операций `can_view_protected`.
- Пользователь выбирает текущую схему из массива `auth.users.data_schema`;
  сервер проверяет выбор по этому же массиву.
- Отсутствующая схема помечается в списке как недоступная. API возвращает
  `409 DATA_SCHEMA_NOT_FOUND`, а данные не загружаются до выбора существующей
  схемы.
- Неавторизованный запрос к API возвращает HTTP 401.
- Выход выполняется POST-запросом с CSRF-токеном.

## 4. Панели операций

Панели «Приход» и «Расход» имеют одинаковую структуру и независимую прокрутку.
При ширине экрана менее 1100 пикселей панели отображаются во вкладках с
сохранением выбранной вкладки в пределах браузерной сессии.

Каждая строка отображает:

| Поле интерфейса | Источник |
|---|---|
| Дата | `actions.action_date` |
| Счёт и валюта | `accounts.name`, `currencies.name` |
| Направление и операция | `directions.name`, `action_types.name` |
| Подоперации 1 и 2 | `suboperations_l1.name`, `suboperations_l2.name` |
| Сумма | `actions.amount` |
| Примечание | `actions.memo` |

Операции сортируются по дате и ID в обратном порядке: сначала новые.

Операции загружаются при прокрутке без видимой постраничной навигации. Каждая
панель имеет независимое положение прокрутки и независимый кэш страниц.

Frontend использует виртуальный список: полоса прокрутки отражает полное число
операций, а в DOM и памяти находятся только видимые строки, небольшой буфер и
не более 20 страниц по 100 операций. Удалённые из LRU-кэша страницы повторно
загружаются при возврате к ним. При перетаскивании ползунка запрос откладывается
на 120 мс, а запросы более неактуальных страниц отменяются.

Backend возвращает операции порциями по 100 строк для позиции, соответствующей
текущему положению полосы прокрутки.

Положение прокрутки преобразуется в `offset`; API возвращает страницу для этого
смещения. SQL сначала выбирает ID нужной страницы по индексу
`(is_debit, action_date DESC, id DESC)`, затем присоединяет справочники.

При изменении любого фильтра обе панели очищаются, запросы устаревших страниц
отменяются, и загрузка начинается с первой страницы. Во время запроса
отображается индикатор загрузки.

### 4.1. Разделение на приход и расход

Разделение выполняется по `actions.is_debit` выбранной схемы:

- `true` — приход;
- `false` — расход.

### 4.2. Отображение значений

- Сумма выводится с двумя знаками после запятой и разделителями тысяч.
- Валюты не смешиваются в одной итоговой сумме без пересчёта.
- Значения `NULL` отображаются знаком `—`.
- Placeholder-элементы справочников отображаются как «Неизвестно (ID: …)».
- Защищённая операция выделяется фоном и цветным акцентом без раскрытия
  дополнительной информации.

## 5. Итоги

В нижней части формы показываются результаты для всей отфильтрованной выборки,
а не только для загруженной страницы.

### 5.1. Итоги по валютам

Для каждой валюты отображаются:

| Валюта | Начальное сальдо | Приход | Расход | Текущее сальдо | Конечное сальдо |
|---|---:|---:|---:|---:|---:|

### 5.2. Итоги по направлениям

Для каждого направления и валюты отображаются:

| Направление | Валюта | Начальное сальдо | Приход | Расход | Текущее сальдо | Конечное сальдо |
|---|---|---:|---:|---:|---:|---:|

Всю таблицу детализации по направлениям можно свернуть или развернуть. Общая
таблица по валютам показывается независимо от детализации по направлениям.

### 5.3. Правила расчёта

- Расчёты выполняются в исходной валюте операции.
- `NULL` в сумме не участвует в расчёте.
- Округление выполняется до двух знаков после запятой.
- Начальное сальдо рассчитывается по операциям, дата которых меньше начальной
  даты выбранного периода, с применением остальных активных фильтров.
- Итоговый приход — сумма операций `is_debit = true` внутри выбранного периода.
- Итоговый расход — сумма операций `is_debit = false` внутри выбранного периода.
- Текущее сальдо за период равно `приход − расход`.
- Конечное сальдо равно `начальное сальдо + текущее сальдо`.
- Конечная дата периода включается целиком.
- Использование `exchange_rate` для дополнительного итога в базовой валюте не
  входит в первую версию и требует отдельного правила пересчёта.
- Защищённые операции участвуют в итогах только при включённом чекбоксе
  «Защищённые».

## 6. API первой версии

Backend предоставляет endpoint авторизации и выбора контекста:

```text
POST /api/login
POST /api/logout
GET  /api/me
POST /api/schema
```

Данные предоставляются через read-only endpoint:

```text
GET /api/lookups
GET /api/actions
GET /api/action-summary
```

`/api/actions` возвращает одну порцию строк для выбранного типа операции. Тип
передаётся параметром `flow=income|expense`, позиция — параметрами `offset` и
`limit`. При `include_total=1` ответ также содержит полное число строк панели.

`/api/action-summary` возвращает:

- итоги по валютам;
- итоги по направлениям и валютам;
- общее количество найденных операций.

Оба endpoint принимают одинаковые параметры фильтрации. Идентификаторы
справочников передаются как целые числа, даты — в формате `YYYY-MM-DD`.
Чекбокс «Защищённые» передаётся параметром `include_protected=1`; отсутствие
параметра или значение `0` означает фильтр `is_black = false`.

Справочники для фильтров загружаются через `/api/lookups`.

## 7. Нефункциональные требования

- Backend: PHP 8.5.
- База данных: PostgreSQL 17; рабочая схема выбирается из профиля пользователя.
- Кодировка ответов: UTF-8.
- Значения фильтров передаются параметрами SQL. Структурные значения SQL
  допускается формировать только после строгой серверной валидации.
- Целевое время ответа для списка и итогов — до одной секунды на текущем объёме
  данных в локальной сети.
- Интерфейс должен корректно работать при ширине от 1280 пикселей.
- При ширине менее 1100 пикселей панели отображаются в отдельных вкладках.
- Первая версия предназначена только для просмотра; добавление и изменение
  операций в неё не входят.

### 7.1. CSS и дизайн-система

- Имена прикладных CSS-классов строятся по БЭМ:
  `.block__element--modifier`.
- CSS-классы отражают компонент интерфейса, а не его положение или содержимое.
- Токены дизайн-системы, базовая типографика, цвета, отступы, радиусы и состояния
  фокуса находятся в отдельном файле `public/css/design-system.css`.
- Стили компонентов находятся в `public/css/app.css`.
- Компоненты используют переменные дизайн-системы вместо собственных цветов и
  размеров.
- `!important` не используется. Inline-стили допускаются только для вычисляемой
  геометрии виртуального списка и позиционирования popover.

## 8. Критерии приёмки MVP

1. Пользователь задаёт период и любую комбинацию справочных фильтров.
2. Обе панели показывают операции из одной отфильтрованной выборки.
3. Операция отображается только в одной из панелей.
4. Итоги рассчитаны по всей выборке и совпадают с контрольными SQL-запросами.
5. Текущее сальдо по каждой валюте равно приходу минус расходу.
6. Каскадные фильтры не предлагают несовместимые значения.
7. Перезагрузка URL восстанавливает выбранные фильтры.
8. Переход к произвольной позиции загружает соответствующую страницу без
   накопления всей выборки в памяти.
9. При выключенном чекбоксе защищённые операции отсутствуют в панелях и итогах.
10. При включённом чекбоксе панели и итоги включают защищённые и обычные
    операции.
11. Прокрутка остаётся плавной при выборке до 250 000 операций, потому что DOM
    содержит только видимые строки.
12. Полоса прокрутки отражает полный размер выборки, а видимые страницы
    загружаются без кнопок и видимого переключения страниц.
13. Для каждой валюты и направления отображаются начальное сальдо, приход,
    расход, текущее и конечное сальдо.
14. Конечное сальдо равно начальному сальдо плюс приход минус расход.
