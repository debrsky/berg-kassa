# WebUI «Касса» — техническое задание

## 1. Назначение и границы системы

Приложение предназначено для просмотра, анализа и ведения финансовых операций
в PostgreSQL. Пользователь работает в одной выбранной схеме из разрешённых ему.

В текущий объём входят: вход и выход, операции прихода и расхода, фильтры,
итоги по валютам, справочники, журнал аудита и управление пользователями.
Отложенные возможности перечислены в разделе 10 и не являются обязательствами
текущей версии.

Документ описывает требуемое поведение. История проверок и исправлений находится
в [отчёте аудита](html-quality-audit.md), команды установки и публикации — в
[README](../README.md). Прохождение отдельных тестов не означает выполнения
всех требований документа.

Термины:

| Термин | Значение |
|---|---|
| Финансовая операция | Запись `actions`; далее «операция», если не оговорено иначе |
| Операция справочника | Элемент `action_types` в каскаде классификации |
| Рабочая схема | Выбранная схема данных PostgreSQL |
| Защищённая операция | Запись с `is_black = true` |
| Защищённый доступ | Право `can_view_protected`, также разрешающее администрирование |
| Сальдо за период | Приход минус расход; не включает начальное сальдо |

## 2. Пользователи и права

### 2.1. Матрица доступа

Все действия с данными ограничены разрешёнными пользователю схемами.

| Действие | Без входа | Без защищённого доступа | С защищённым доступом |
|---|---|---|---|
| Вход | Да | — | — |
| Просмотр и изменение обычных операций | Нет | Да | Да |
| Просмотр и изменение защищённых операций | Нет | Нет | Да |
| Просмотр справочников | Нет | Да | Да |
| Создание, изменение и удаление справочников | Нет | Нет | Да |
| Просмотр журнала аудита | Нет | Нет | Да |
| Управление пользователями | Нет | Нет | Да |
| Выбор разрешённой схемы и выход | Нет | Да | Да |

Сервер проверяет права независимо от видимости кнопок и переданных параметров.
Скрытые элементы интерфейса не являются средством защиты. Отказ в изменении
справочника или доступе к административной странице/API возвращает HTTP 403.

### 2.2. Вход и выбор схемы

- Вход по логину и паролю, сессия PHP. API без авторизации возвращает HTTP 401;
  закрытые страницы перенаправляют на вход.
- Для поля пароля задан `autocomplete="off"` — запрос браузеру не сохранять
  значение, а не гарантия управления менеджером паролей.
- Выход выполняется POST с CSRF-токеном.
- Разрешённые схемы хранятся в массиве `auth.users.data_schema`; сервер проверяет
  выбор по этому массиву.
- Отсутствующая схема помечается недоступной. API возвращает
  `409 DATA_SCHEMA_NOT_FOUND`; данные не загружаются до выбора существующей схемы.

## 3. Общий интерфейс

### 3.1. Навигация и темы

На авторизованных страницах есть «Меню ▾»: «Справочники», «Журнал аудита»,
«Пользователи», затем «Выйти» после разделителя. На внутренних страницах
добавляется ссылка «Операции». Пункты ограничены матрицей прав раздела 2.
Меню закрывается после выбора, клика снаружи или Escape; Escape возвращает
фокус на кнопку меню.

На всех страницах есть кнопка темы 36 × 36 px. Цикл: системная → светлая →
тёмная. Иконки: монитор, солнце, луна; есть подсказка и доступная подпись.
Размер кнопки не меняется. Выбор сохраняется в браузере; системная тема следует
`prefers-color-scheme`.

### 3.2. Главная страница

Страница содержит панель фильтров, область операций и таблицу итогов.
При ширине от 1100 px приход и расход расположены рядом, при меньшей ширине —
во вкладках. Выбранная вкладка сохраняется в браузерной сессии. Фильтры и итоги
общие для двух панелей, положение прокрутки каждой панели независимо.

На смартфоне форма операции открывается на весь экран; заголовок и кнопки
действий остаются доступны при прокрутке, элементы управления имеют увеличенную
область касания. Общие требования к адаптивности и доступности — в разделе 8.2.

## 4. Финансовые операции

### 4.1. Просмотр

| Поле | Источник |
|---|---|
| Дата | `actions.action_date` |
| Счёт и валюта | `accounts.name`, `currencies.name` |
| Направление и операция справочника | `directions.name`, `action_types.name` |
| Подоперации | `suboperations_l1.name`, `suboperations_l2.name` |
| Сумма и примечание | `actions.amount`, `actions.memo` |

`is_debit = true` означает приход, `false` — расход. Сортировка: дата, затем
ID по убыванию. Операция принадлежит только одной панели. Суммы отображаются
с двумя знаками после запятой и разделителями тысяч; отсутствующие значения —
«—». Служебные placeholder-записи показываются как «Неизвестно (ID: …)».
Защищённые операции выделяются фоном и цветным акцентом.

Операции загружаются при прокрутке без кнопок страниц. При применении фильтра
обе панели сбрасываются к началу, запросы устаревших страниц отменяются,
показывается загрузка. Технические ограничения списка — в разделе 8.1.

### 4.2. Фильтры

До загрузки пользователя и справочников панель фильтров заблокирована.
Переключение схемы недоступно до готовности страницы и на время смены схемы.
Все фильтры действуют совместно на приход, расход и итоги. Применённые значения
сохраняются в URL и восстанавливаются после перезагрузки. «Сбросить» очищает
поиск и выборы, выключает «Защищённые», возвращает последние 30 дней;
после сброса действуют правила автоматического выбора каскада.

| Фильтр | Правило |
|---|---|
| Период | Поля «С» и «По» и готовые периоды, см. 4.3 |
| Примечание | Вхождение текста без учёта регистра, см. ниже |
| Счёт, валюта | Одиночные справочные списки, пустое значение — «Все» |
| Направление → операция справочника → подоперация 1 → подоперация 2 | Каскад одиночных списков |
| Защищённые | Выключен: только `is_black=false`; включён: обычные и защищённые |

Чекбокс «Защищённые» доступен только при соответствующем праве. Сервер
игнорирует попытку пользователя без права включить защищённые записи.

Справочные фильтры не имеют текстового поиска. При изменении родителя каскад
обрабатывается последовательно:

1. Очистить выбранные значения всех дочерних уровней.
2. Для следующего уровня определить варианты по выбранному родителю.
3. Если родитель не выбран — заблокировать уровень и всех его потомков.
4. Если вариант ровно один — выбрать его и повторить обработку следующего уровня.
5. Иначе разрешить выбор доступного уровня; его потомки остаются заблокированными
   до выбора родителя.

Поиск по примечанию применяется через 400 мс после последнего ввода, по Enter —
сразу; очистка снимает поиск сразу. `%`, `_` и `!` ищутся буквально.
Поле ограничено 500 символами; ограничение API приведено в разделе 7.2.

### 4.3. Период

При первом открытии — последние 30 календарных дней, включая сегодня.
Конечная дата включается целиком; подсказки объясняют пустые границы.

| С | По | Выборка |
|---|---|---|
| Дата | Дата | От начала первого дня до конца последнего |
| Пусто | Дата | Без нижней границы, до конца указанного дня |
| Дата | Пусто | Начиная с указанного дня, без верхней границы |
| Пусто | Пусто | За всё время |

При двух заполненных границах начало не может быть позже конца: интерфейс
показывает ошибку, сохраняет последнюю применённую выборку; API отклоняет запрос.
Очистка клавиатурой снимает границу, в том числе когда браузер считает частично
удалённую дату некорректной. Ручная правка сбрасывает название готового периода.

| Готовый период | Начало | Конец |
|---|---|---|
| Сегодня | Сегодня | Сегодня |
| Вчера | Вчера | Вчера |
| Эта неделя | Понедельник текущей недели | Сегодня |
| Этот месяц | Первый день текущего месяца | Сегодня |
| Прошлый месяц | Первый день прошлого месяца | Последний день прошлого месяца |
| Последние 30 дней | Сегодня минус 29 дней | Сегодня |
| За всё время | Пусто | Пусто |

Выбор сразу устанавливает обе границы и применяет фильтры. Календарные периоды
интерфейса вычисляются по локальной дате браузера. При прямом API-запросе без
дат значения по умолчанию вычисляются по часовому поясу PHP-сервера. API
принимает календарные даты без смещения; сравнение с данными выполняет БД.
Единый фиксированный часовой пояс сейчас не задан: введение такого правила
потребует отдельного изменения, а не редакционной правки ТЗ.

### 4.4. Создание, изменение и удаление

«+ Добавить» у панели открывает диалог с выбранным типом прихода/расхода.
Для редактирования используются двойное нажатие на строку или нажатие на дату
(в том числе на смартфоне).

Форма содержит тип, дату и время, счёт, валюту и курс, каскад классификации,
сумму, примечание и признак защищённости. Сервер проверяет обязательность,
типы, положительные сумму и курс, существование справочных записей и права.

Для новой операции:

- Справочные фильтры и признак защищённости подставляются в соответствующие поля.
- Валюта по умолчанию — `р.`, но выбранная валюта фильтра имеет приоритет.
- При выборе валюты курс берётся из последнего ненулевого `currency_rates`
  по дате и ID; для `р.` без истории — 1. Пользователь может изменить курс.
- В каскаде единственный доступный вариант выбирается автоматически.

«Выполнить проводку» доступно только при создании. Пользователь выбирает счёт
и подоперацию 2, ограниченную выбранной подоперацией 1. Сервер в одной транзакции
создаёт вторую операцию противоположного типа с теми же датой, суммой, валютой,
курсом, примечанием и защищённостью. Ошибка любой части отменяет обе записи.
После создания операции независимы.

После сохранения или удаления обновляются списки и итоги. Сохранённая запись
показывается только если соответствует активным фильтрам. Удаление физическое,
после отдельного подтверждения. Общие правила отправки форм — в разделе 8.2.

## 5. Итоги и формулы

Таблица содержит только итоги по валютам, без отдельного заголовка, подписи
периода и счётчика. Доступное название раздела — «Итоги и сальдо».

Расчёт выполняется по всей отфильтрованной выборке, а не по загруженным строкам.
Справочные фильтры, поиск по примечанию и защищённость влияют и на начальное
сальдо. Валюты не смешиваются; пересчёт через `exchange_rate` не выполняется.
`NULL` в сумме не участвует в расчёте; результат округляется до двух знаков.

| Столбец | Правило |
|---|---|
| Валюта | Исходная валюта операций |
| Начальное | Приход минус расход до начала периода; без нижней границы — 0 |
| Приход | Сумма приходов внутри периода |
| Расход | Сумма расходов внутри периода |
| За период | Приход − расход |
| Конечное | Начальное + приход − расход |

Без верхней границы учитываются все операции начиная с нижней границы.

## 6. Справочники и администрирование

### 6.1. Справочники

Страница `/references`: счета, валюты, курсы валют, направления, операции
справочника и подоперации двух уровней. Доступ определяется разделом 2.
Без права изменения доступны списки, поиск и каскад; форма и кнопки изменения скрыты.

Операции справочника и подоперации показаны в трёх связанных колонках;
направление задаётся над ними. В колонке есть поиск, добавление и редактирование.
Выбор записи фильтрует следующий уровень; двойное нажатие или карандаш открывает
форму. На смартфоне колонки перелистываются горизонтально, форма находится ниже.
Для зависимых справочников в форме выбирается родитель. Ручное изменение
служебной записи снимает `is_placeholder`.

Backend разрешает только известные таблицы и поля. Перед удалением проверяет
зависимости независимо от наличия внешних ключей:

| Удаляемая запись | Что блокирует удаление |
|---|---|
| Счёт | Финансовые операции |
| Валюта | Операции, счета, курсы |
| Направление | Операции справочника |
| Операция справочника | Подоперации 1 |
| Подоперация 1 | Подоперации 2 |
| Подоперация 2 | Финансовые операции |

При использовании записи — HTTP 409 и сообщение с количеством использований.
Внешние ключи дополнительно защищают от конкурентных изменений.

### 6.2. Пользователи

Страница `/users` позволяет просматривать, создавать и изменять пользователей:
логин, схемы, активность и защищённый доступ. Пароль обязателен при создании,
при редактировании пустое поле оставляет текущий пароль. Хеш API не возвращает.
Нельзя отключить себя или отозвать собственный защищённый доступ.
Изменения пользователей записываются в аудит без паролей и хешей.

### 6.3. Журнал аудита

`auth.audit_log` хранит дату, событие, пользователя/логин, IP, рабочую схему,
объект и детали. Записываются успешные/неуспешные входы, ограничение попыток,
выход, смена схемы, отказы доступа, создание/изменение/удаление данных.
Для изменений сохраняются состояния до и после; пароли и CSRF-токены исключены.
Изменение данных и его аудит фиксируются одной транзакцией.

Страница `/audit` показывает записи и JSON-детали, фильтры по периоду, событию
и логину; страницы по 50 записей. Редактирования и удаления через UI/API нет.
Доступ приложения к странице и API определяется матрицей раздела 2.

Прямой доступ к таблице — отдельные права БД: административные роли обслуживают
журнал, рабочей роли приложения запрещены UPDATE и DELETE. Добавление событий
приложением разрешено. Хранение по умолчанию — 180 дней; удаление старых событий
выполняется `php bin/prune-audit-log.php 180` административной ролью.

## 7. API

### 7.1. Маршруты

API возвращает JSON. Изменяющие запросы передают JSON и, кроме входа,
`X-CSRF-Token`. Права перечислены в разделе 2.

| Метод и путь | Назначение |
|---|---|
| POST `/api/login` | Вход |
| POST `/api/logout` | Выход |
| GET `/api/me` | Текущий пользователь, схемы, права, CSRF-токен |
| POST `/api/schema` | Выбор схемы |
| GET `/api/lookups` | Справочники для фильтров и форм |
| GET `/api/actions` | Страница операций |
| POST `/api/actions` | Создание операции и необязательной проводки |
| PUT, DELETE `/api/actions/{id}` | Изменение/удаление операции |
| GET, POST `/api/references/{type}` | Просмотр/создание справочной записи |
| PUT, DELETE `/api/references/{type}/{id}` | Изменение/удаление записи |
| GET `/api/audit-log` | Просмотр журнала |
| GET, POST `/api/users` | Просмотр/создание пользователя |
| PUT `/api/users/{id}` | Изменение пользователя |
| GET `/api/action-summary` | Итоги по валютам и число операций |

### 7.2. Параметры выборки

Общие параметры `/api/actions` и `/api/action-summary`:

| Параметр | Значение и пустое состояние |
|---|---|
| `from_date`, `to_date` | `YYYY-MM-DD`; явно пустое значение снимает соответствующую границу |
| Отсутствующий параметр даты | Соответствующая дата последних 30 дней, см. 4.3 |
| `all_time=1` | Снимает обе границы, имеет приоритет над датами |
| `memo` | Строка до 2000 байт; пусто/отсутствует — без поиска; литеральный параметризованный ILIKE |
| `account_id`, `currency_id`, `direction_id`, `action_type_id`, `suboperation_l1_id`, `suboperation_l2_id` | Положительный целый ID; пусто/отсутствует — без ограничения |
| `include_protected=1` | Обычные и защищённые, только при наличии права; иначе только обычные |

Только для `/api/actions`:

| Параметр | Ограничение |
|---|---|
| `flow` | Обязателен: `income` или `expense` |
| `offset` | Неотрицательное целое, по умолчанию 0 |
| `limit` | 1–200, по умолчанию 100 |
| `include_total=1` | Добавить число всех операций выбранной панели |

Ответ операций содержит `items` и `total` (без запроса подсчёта — null).
Ответ итогов содержит `currencies` и `operation_count`.
Для журнала: `offset` от 0, `limit` 1–100 (по умолчанию 50), необязательные
`event`, `login`, `from_date`, `to_date`. Правила пустых границ и `all_time`
выше относятся к операциям и итогам, не к журналу.

### 7.3. Основные ответы об ошибках

| HTTP | Значение |
|---|---|
| 400 | Некорректные параметры или данные |
| 401 | Требуется вход или неверные учётные данные |
| 403 | Недостаточно прав или неверный CSRF-токен |
| 404 | Не найдена запрошенная запись/маршрут |
| 405 | Метод не поддерживается |
| 409 | Конфликт: отсутствующая схема, используемый справочник, занятый логин |
| 429 | Ограничение частых попыток входа |
| 500 | Внутренняя ошибка без раскрытия подробностей клиенту |

Сообщение передаётся в `error`; отсутствующая схема дополнительно имеет
`code=DATA_SCHEMA_NOT_FOUND` и `schema`.

## 8. Безопасность и технические ограничения

### 8.1. Системные требования и эксплуатация

- PHP 8.5, PostgreSQL 17, UTF-8. Изменение структуры рабочих схем для операций
  не требуется.
- Виртуальный список хранит видимые строки, буфер и не более 20 страниц по
  100 операций. LRU-вытесненные страницы загружаются повторно при возврате.
  При прокрутке запрос откладывается на 120 мс; неактуальные запросы отменяются.
- Полоса прокрутки отражает полное число записей. Позиция преобразуется в offset;
  SQL сначала выбирает ID страницы с использованием индекса
  `(is_debit, action_date DESC, id DESC)`, затем присоединяет справочники.
- Цель для отдельного чтения списка/итогов — до секунды в локальной сети.
  Это ориентир, а не доказанный SLA: объём и характеристики среды должны быть
  записаны при измерении. Действующий автоматический порог приведён в разделе 9.
- Целевой объём — до 250 000 операций. Проверяемый инвариант: DOM и кэш ограничены
  видимой областью и заданным лимитом, а не размером всей выборки. Этот инвариант
  не гарантирует плавность; её оценивают отдельно в сценарии прокрутки.
- Стили и токены разделены: `public/css/design-system.css` и `public/css/app.css`.
  Классы — БЭМ, отражают компонент, а не расположение. Цвета/размеры берутся из
  токенов; `!important` запрещён. Inline-стили допустимы для вычисляемой геометрии
  виртуального списка и позиционирования popover.
- Выгрузка `bin/deploy-hosting.ps1` сначала идемпотентно обновляет служебную схему
  `auth`, затем загружает приложение. Это не восстановление рабочих данных.

#### Требование к сетевому соединению

Для штатной работы необходимо устойчивое сетевое соединение между браузером
и сервером приложения, а также между сервером приложения и PostgreSQL.
Соединение должно сохраняться на протяжении запроса и получения ответа.
Работа при длительных обрывах, зависании передачи или падении скорости до нуля
не является поддерживаемым режимом. Автономная работа не предусмотрена.

При несоблюдении требования возможны следующие последствия:

- Длительное ожидание загрузки или сохранения, блокировка элементов управления:
  приложение не задаёт собственный предельный срок ожидания всех запросов.
- Неполная загрузка списков, отображение старых итогов и несоответствие видимых
  данных выбранным фильтрам до успешного обновления.
- Отсутствие автоматического восстановления после возвращения связи;
  может потребоваться повторное чтение данных или перезагрузка страницы.
- Неопределённый результат сохранения или удаления: сервер мог выполнить
  действие, даже если браузер получил ошибку или не получил ответ.
- Повторная отправка создания после потери ответа может создать дубликат
  операции или пары проводки. Блокировка кнопки не защищает от такого повтора;
  серверная идемпотентность не реализована.
- После обрыва при смене схемы выбранная схема на сервере и отображаемые данные
  могут расходиться до повторной загрузки и проверки текущей схемы.
- Несохранённый ввод может быть потерян при перезагрузке или закрытии страницы;
  восстановление черновиков не предусмотрено.

При неизвестном результате записи пользователь должен восстановить связь,
проверить текущую схему и наличие/состояние операции перед повторным действием.
Ошибка сети сама по себе не подтверждает, что запись не выполнена. До проверки
схемы и актуальности данных продолжать изменения не следует.

Транзакции БД обеспечивают совместную фиксацию операции, проводки и аудита,
но не гарантируют доставку ответа браузеру или отсутствие дублей при повторе.
Дополнительные механизмы идемпотентности, автономной очереди и восстановления
незавершённых отправок в текущий объём проекта не входят. Существующая обработка
явных ошибок и защита от устаревших ответов сохраняются.

### 8.2. Качество HTML и интерфейса

**HTML-01. Документ и структура.** Используется HTML Living Standard:
`<!doctype html>`, UTF-8, `lang="ru"`, уникальный осмысленный `title` для каждой
страницы, `viewport` без запрета масштабирования. Проверять итоговый HTML после
PHP и динамического рендеринга: уникальность `id`, правильную вложенность,
ссылки `for`/ARIA на существующие элементы, отсутствие вложенных форм и
интерактивных элементов внутри кнопок/ссылок. Проверка выполняется по коду и DOM средствами существующего Playwright;
установка отдельного HTML-валидатора не требуется.

**HTML-02. Семантика.** На странице один основной `main` и понятная структура
заголовков. Переходы — ссылки с `href`, действия — кнопки с явным `type`.
Таблицы имеют заголовки столбцов; диалог имеет доступное название. Нативные
элементы предпочтительнее их имитаций через `div`; ARIA дополняет семантику.
Визуально скрытая информация не должна создавать доступные пустые элементы.

**A11Y-01. Доступность.** Цель — применимые критерии WCAG 2.2 уровня AA.
Ключевые проверки: клавиатура без ловушек, видимый и не перекрытый фокус,
доступные названия полей, кнопок и диалогов, понятные сообщения об ошибках.
Динамические результаты и ошибки объявляются скринридером. Текстовый контраст
не ниже 4,5:1 (крупный текст — 3:1), значимые нетекстовые элементы — 3:1.
Цели указателя — не менее 24 × 24 CSS px либо удовлетворяют исключениям
стандарта. Проверять светлую, тёмную и системную темы. В приёмку входят проверка кода и доступных имён средствами Playwright;
установка и проверка NVDA/VoiceOver не требуются.

**LAYOUT-01. Адаптивность.** Проверять ширины 320, 390, 768 и 1280 CSS px,
увеличение текста до 200% и перекомпоновку при масштабе 400% на экране 1280 px.
На странице нет общей горизонтальной прокрутки и перекрытия управления.
Двумерные таблицы могут прокручиваться внутри собственного контейнера.
Длинные примечания, названия, пустые списки и модальные формы сохраняют
доступность управления. Эмуляция ширины не заменяет проверку реального zoom.

**FORM-01. Формы.** Каждое поле имеет постоянную подпись; placeholder её не
заменяет. Тип поля соответствует данным, autocomplete/inputmode задаются по
назначению. Ошибка доступна текстом и связана с полем, введённые значения
сохраняются. Проверка на клиенте дополняет серверную. Повторное нажатие или submit той же формы во время сохранения
блокируется. Это защита от двойного действия в интерфейсе, а не гарантия
идемпотентности при сетевом повторе после неизвестного результата запроса. При отключённом JavaScript показывается понятное сообщение;
формы входа и редактирования не отправляют данные методом GET.

**SEC-01. Безопасность.** Пользовательский текст выводится через `textContent`,
`Option` или контекстное экранирование, а не как исполняемый HTML. SQL использует
параметры и разрешённый список идентификаторов. Сервер проверяет авторизацию,
доступ к схеме, защищённым данным и CSRF на каждой изменяющей операции.
На хостинге обязательны HTTPS, защищённая сессия, CSP и запрет встраивания.
Чувствительные ответы не кэшируются. Проверка заголовков проводится на
хостинге: локальный PHP-сервер не применяет `.htaccess`. `noindex` не заменяет
контроль доступа; пароли и токены не попадают в URL и диагностические отчёты.

**RESILIENCE-01. Ошибки и ожидание.** Загрузка, пустой результат и ошибка
различимы. Сбой сети при чтении, сохранении или выходе даёт понятное сообщение
и возможность повторить действие. Старый ответ не перезаписывает более новый
выбор; для справочников и журнала игнорируются как устаревшие данные, так и
устаревшие ошибки. Управление, зависящее от загрузки, становится доступным после готовности.
Неперехваченных исключений и отклонённых Promise в штатных сценариях нет.

**PERF-01. Производительность.** Сохраняются виртуализация и ограничение кэша
операций. Количество строк DOM не растёт пропорционально всей выборке.
Скрипты не блокируют разбор документа без необходимости; статические ресурсы
версионируются. Проверять задержку поиска, прокрутку и скачки компоновки;
наличие `defer` само по себе не доказывает достаточную производительность.

**COMPAT-01. Браузеры.** Обязательная проверка выполняется в уже установленном
Chromium через Playwright: настольный режим и эмуляция Pixel 7. Установка
дополнительных браузеров и проверка Firefox, Safari/iOS или Edge не требуются.
Поддержка этих браузеров отдельно не подтверждается.

**QA-01. Приёмка.** Для пяти страниц (вход, операции, справочники, аудит,
пользователи), меню и диалога проверять HTML, доступность и адаптивность.
Повторить значимые сценарии с ограниченными правами, пустыми результатами,
ошибкой сети и длинным текстом. Полный `npm test` обязателен. Разметка,
доступность и адаптивность проверяются по коду и средствами существующего
Playwright. Отдельные HTML-валидаторы, скринридеры и дополнительные браузеры
не входят в обязательную приёмку; устанавливать их не требуется.
В отчёте разделять подтверждённые результаты и нарушения. Такой объём проверки
не является сертификацией полного соответствия WCAG или всех браузеров.
Пропущенный тест не считается успешным. Результаты проверок фиксируются отдельно от требований.

Нормативные источники: [HTML Living Standard](https://html.spec.whatwg.org/multipage/)
и [WCAG 2.2](https://www.w3.org/TR/WCAG22/). Выбор браузеров, сценарии ошибок и
процесс релиза выше — требования данного проекта.

## 9. Приёмка

### 9.1. Обязательный объём

`npm test`: статические проверки PHP/JS/Python, unit, проверка схемы и
целостности данных, API и браузерные тесты в установленном Chromium
(настольный режим и Pixel 7). CRUD-тесты используют временные записи и очищают
их. Никаких дополнительных валидаторов, скринридеров или браузеров устанавливать
не требуется; ограничения доказанного покрытия указываются в отчёте.

Результат релиза: команды, количество успешных/пропущенных/ошибочных проверок,
версия браузера и конкретные оставшиеся проблемы. Пропуск не считается успехом.
Числа последнего прогона не являются частью требований и хранятся в отчёте.

### 9.2. Сценарии

### 9.3. Производительность

Существующий API-тест одновременно читает lookups, приход, расход и итоги;
в обычном прогоне вся группа должна завершиться менее чем за 2000 мс.
В отчёте фиксируется используемая база/схема и среда, без секретов.

Отдельный `npm run test:load` выполняет повторный read-only прогон; он не входит
в обычный `npm test`. В нагрузочном режиме проверка двухсекундного порога
отключена: такой прогон проверяет успешность чтений под нагрузкой, а не SLA.

## 10. Отложенные возможности

Не входят в текущую приёмку:

- Общий итог в базовой валюте через `exchange_rate` — нужны правила пересчёта.
- Отображение курса в строке операции.
- Текстовый поиск в справочных фильтрах и множественный выбор счетов/валют.
- Выгрузка в Excel/CSV.

Единый фиксированный часовой пояс и гарантия идемпотентности сетевых повторов
не вводятся этой редакцией; текущее поведение описано в 4.3 и FORM-01.
